# 当前环境约 28 像素小码：修复与实测

本次修复后的正常相机固件已通过 COM4 烧录并留在 P4。优化前的远程备份为 main 的 1f1b1da。本次改动限于固件解码和回归工具。

## 原因与修复

最初三帧标签完整入镜，原图能够解出 012345。10×10 的码体短边只有约 27–28 像素，默认 2 像素步长使每模块只剩约 1.4 个采样点。定位边仍可见，但交替边容易断裂，无法稳定形成候选四边形。另一个限制是旧角点精修拒绝短于 32 像素的边，即使读出了码值，也可能无法输出坐标和姿态。

现在每帧从自己的粗二值图中寻找短实心 L 边，容忍一个采样点的断裂；结合内部黑白跳变和周围小标记给候选排序。最多保留 12 个区域，每个区域通常仅几十像素宽。在原始 Gray8 中进行 1 像素定位，而非全幅改用 1 像素。先快速检查高分候选，再进行局部 Otsu 和必要的两倍插值补救。所有结果仍须通过原 ECC200 校验。

小码搜索具有独立的 32 ms 上限，同时受帧自身截止时间限制，每个候选也有时间上限。没有复用上一帧的位置、搜索步长或成功阈值。普通码的原搜索路径和外标记路径保留。

对于 10×10 的小码，角点精修最低边长改为 22 像素，缩小切向平滑与法向搜索范围；仍要求四边拟合、有效交点、凸性和支持点数通过检查。未直接把粗坐标标成精修坐标。

## P4 现场结果

环境：ESP32-P4 rev 1.3，CPU 360 MHz，PSRAM 200 MHz，OV9281 1280×720、50 fps 取帧。最后一轮在用户确认固定相机、标签及光照后测量。测试前后均为正常相机程序，未使用 PC 代替 P4 解码。

| 工况 | 时长 | 成功/尝试 | 成功率 | 有效解码吞吐 | 单帧平均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原现场，修复前 | 5.015 s | 0/48 | 0% | 0 次/s | 132.5 ms |
| 最终版，关闭图片上传 | 12 s | 537/537 | 100% | 44.75 次/s | 43.5 ms |
| 最终版，每 200 ms 请求图片 | 10 s | 378/378 | 100% | 37.8 次/s | 46.0 ms |

上传测试收到 49 张图片，所有完整结果报文内容均为 012345。主机从流中间开始接收时，两次记录各有一条残缺的首行，未用于上表的逐帧成功率统计。双核同时处理不同帧，因此吞吐量不能按单帧延迟的倒数计算。帧号出现跳跃表示处理队列保留较新的画面，并不等于尝试解码失败。

关闭上传时 Core 0 / Core 1 平均占用率为 88.3% / 93.5%；上传时为 89.8% / 88.9%。上传工况仍低于 40 次/s，不能把 44.75 次/s 当成包含图片上传的结果。

测试后的额外原始帧编号 4712，板端 success=true，耗时 38.059 ms，原图 CRC32 为 D3E9D121。见[原始帧记录](small_code_live_20261119/verified_scene.json)。

上述 100% 仅表示这两段有限时长实测均成功，不代表所有距离、运动和光照条件。测试期间另存了位置和亮度变化后的失败帧；其中更暗且运动中的图像仍可能无法读码。
