# 粘连定位标记局部重分割：集成与实测

日期：2026-11-18。ESP-IDF 5.4.0，ESP32-P4 rev1.3，COM4 烧录、COM65 采集。

## 改动与原因

小标签的纸面偏暗、上方背景偏亮时，均值阈值可能把纸面与上方两个定位方块连成一个长条。原算法拒绝这个长条后，需要进入4像素采样及小窗口补救。

最终方案保留原均值二值化，仅在**当前帧6像素粗搜索**遇到不符合方块比例的长连通域时，读取这个域内的原始灰度，使用整数Otsu再分两类，保留较暗部分，并交回现有连通域和定位验证流程。它没有使用上一帧位置。

处理流程：

1. 原均值阈值生成粗网格掩膜，原洪泛搜索取得连通域。
2. 对宽高各2～64个采样点、至少8点、长宽比例超过约1.67的域，建立256级灰度直方图。
3. 灰度跨度至少12，分割后两类各至少4点、均值差至少12，才恢复较暗的点。
4. 原扫描重访恢复的点；恢复点带标记，不递归重分割。
5. 继续原三标记组合、透视归一化、DataMatrix校验和角点精修；未成功仍走原4像素常规窗口、小窗口路径。

每次搜索分片最多尝试8个域，累计最多4096点；累计修复函数耗时达到1000 µs后不再启动下一次尝试。**这是启动预算，不是单帧严格1 ms上限**，不含恢复点的后续连通域遍历。直方图使用512字节栈空间，复用已有队列和掩膜，没有新增整帧缓冲或堆分配。4像素搜索不启用这项重分割，避免在正常帧的细搜索中反复增加工作。

产品代码位置：`port/components/xcr_decoder/src/xcr_dmtx.c`，`MarkerSplitBudget`、`split_elongated_marker()`、`finish_marker_roi_slice_step()`。

示意图见[研究阶段对照](../binarization_20261118/background_exploration/component_comparison.png)。两个UI本轮未修改。

## 实际C代码回放

原代码与最终集成代码共1185组对照：既有成功用例退化0组，新增误解码0组，原本失败而新增成功0组。61组ASan/UBSan检查通过。逐组数据见[host_regression.json](host_regression.json)。

`Downloads/captures`归档的5张图，各做6×6采样相位平移，共180组：最终版180/180成功，其中173组直接在6像素粗网格完成，7组仍需4像素；旧版仅2组在6像素完成。**人工平移不是180张独立现场照片，且这批图旧版最终也能全部解出**，收益是提前完成定位，不是新增180个可解场景。此前中值阈值退化的3张原图保持成功。

## 最终板端对照

每组重启后预热3秒、测量20秒。有码和上传测试保持同一标签与光照；无码对照由用户完整遮住码体及外部标记。两版均从重启后的搜索状态开始。上传组每200 ms请求一张解码帧JPEG，不是实时UVC流。

| 场景 | 旧版平均耗时 | 最终版平均耗时 | 旧版成功结果/秒 | 最终版成功结果/秒 |
|---|---:|---:|---:|---:|
| 有码，关闭图片上传 | 27.31 ms | 27.56 ms | 49.70 | 49.36 |
| 有码，开启图片上传 | 29.96 ms | 30.03 ms | 44.65 | 45.15 |
| 完整遮挡，无码 | 54.73 ms | 55.32 ms | 0 | 0 |

有码关闭上传成功比例为旧版98.81%、最终版98.50%；开启上传为旧版98.56%、最终版99.34%。这些是本轮20秒窗口的观测值，不能据小幅差异宣称成功率提升。上传组分别收到97、95张图片。

无码组旧版测得557次处理、最终版545次，全部没有成功结果或误解码；平均增加0.59 ms，约1.1%，P95由68.10变为68.93 ms。最终版并未证明无码更快，局部补救有少量开销。

| 场景 | 旧版Core0 / Core1 | 最终版Core0 / Core1 |
|---|---:|---:|
| 有码，关闭上传 | 80.77% / 72.08% | 80.07% / 73.30% |
| 有码，开启上传 | 81.02% / 75.17% | 81.00% / 76.09% |
| 完整遮挡，无码 | 55.84% / 97.25% | 55.34% / 97.42% |

耗时口径为`@TIMING`：从该帧解码流程开始到后段及角点精修结束，包含前后段排队等待；不含UART发送和姿态计算，也不是单核纯算法耗时。双核流水线可重叠处理不同帧，所以成功结果/秒不等于1000除以这项延迟。丢弃或被新帧替换的帧不会都产生`@TIMING`，因此成功比例也不是全部CSI帧的成功比例。

**结论：正常现场速度基本持平，当前无明显板端加速；可确认的收益是保存的粘连样本更多在粗搜索完成，且本次回放没有退化。** 板端保留成功后的搜索参数，因此冷启动回放中减少细搜索的比例不能直接换算成持续帧率提升。

早期试验混入了不同搜索历史、重启条件，以及遮挡不完整的场景；另有同时启用4像素重分割的中间版。这些数据不用于上述最终对照。

## 数据与复现

- `baseline_code_matched.json`、`final_code_matched.json`：关闭上传。
- `baseline_code_upload_matched.json`、`final_code_upload_matched.json`：开启上传。
- `baseline_no_code_final_pair.json`、`final_no_code_cold.json`：最终无码对照。
- `final_restored_smoke.json`：恢复标签后最终固件的简短解码与上传检查，不参与20秒性能比较。
- `final_restored_settled.json`、`final_restored_upload_settled.json`：场景稳定后的最终固件短测，均为100%成功；上传组收到20张图片。

恢复标签后的第一次短测为83.6%成功，平均35.16 ms；稳定后关闭上传6秒301次全部成功（平均27.87 ms）、开启上传4秒181次全部成功（平均30.25 ms）。第一次短测的波动原因未单独验证，不能据此判定为算法退化或曝光过渡；恢复后的短测也不替代前面的同条件20秒对照。

- `host_regression.json`：实际C集成回放结果；全部成功且载荷一致的用例中，8264个角点坐标最大变化1 px，P95为0。
- `firmware_manifest.json`：最终固件与解码源文件的SHA256。
- `tools/check_component_split_integration.py`：WSL回放及Sanitizer检查；依赖本机`build/component_split_integration_20261118`中的旧版源文件和现有主机探针构建产物。
- `tools/benchmark_component_split_board.py`：板端采集，例如`python tools/benchmark_component_split_board.py --output result.json --seconds 20 --upload`；省略`--upload`即关闭图片上传。

最终固件`build/p4scan_ov9281.bin`大小893952字节，已经重新烧录到P4并通过写入哈希校验。旧版备份留在本机`build/component_split_integration_20261118/baseline_firmware.bin`。没有擦除NVS，没有在本轮提交或推送Git。
