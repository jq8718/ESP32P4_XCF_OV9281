STM32 二维码扫码头定位链路计算原理
核对日期：2026-11-16
工程：/home/sionhu-xctech/R550_C30D-vscode
适用目标：STM32F407VET6，默认 zlac 应用，wheel-qr-v5 版本
文件编码：UTF-8

本文以当前 C 源码为准，说明二维码 ID、四个像素角点如何得到相对测量，
再如何换算车体在二维全局地图中的 x、y、yaw。PC 独立测试程序仅用于核对
数学原理；PC 与 STM32 各自运行，STM32 不调用 PC 解算服务。


1. 当前已经具备什么，哪些链路还未接通

当前 STM32 的定位输入设计为“实际双轮速度＋二维码角点”，没有 IMU 输入。
二维码位姿算法是项目内纯 C 实现的 IPPE 双候选初解＋有界 LM 重投影优化。
STM32 不依赖 OpenCV、Eigen 或第三方视觉、矩阵、滤波算法库。

需要区分以下三层：

（1）已进入默认主程序的内容
    双轮实际速度积分得到连续局部里程计；UART4 二进制扫码接收服务；
    ID／角点／时间校验；STM32 原生相对位姿计算；诊断输出。
    这表示程序已具备处理合规输入的能力，不表示真实扫码设备已经接通。

（2）已实现、可测试，但缺少实测配置的内容
    竖直墙面码的地图位姿换算，STM32 独立六参数相机外参设置，
    二维码尺寸及地图锚点登记接口。
    当前默认外参 CONFIGURED=0，主程序尚未登记实际码表。

（3）尚未接入实际主循环的内容
    当前真实扫码头的 USB Host CDC 接收与协议适配；
    全局轮速＋二维码 EKF 更新；测量时刻对齐及延迟历史回放；
    实测二维码观测协方差和完整全局定位状态管理。

当前真实 ESP32-P4 OV9281 扫码头按 STM32_CDC_PROTOCOL.md 输出 USB CDC 文本。
当前 STM32 默认固件接收的是 UART4 V2 二进制，两者接口和编码不同，尚未互通。
固件没有 USB Host CDC 驱动，USB D+/D− 不能直接接到 UART TX/RX。

因此，当前统一遥操网页上方的连续位姿属于轮速局部 odom，二维码诊断是
另一组测量。当前不能把它描述成已经运行的“二维码纠偏后的全局融合位姿”。
本文中的地图计算公式是现有几何代码的行为；EKF 部分会明确标注为待接入。


2. 完整执行链路及模块职责

实际设备的 PC 独立测试路径：

    OV9281 图像
       |
    ESP32：识别码的 ID 和四个原图像素角点
       |
    USB CDC 文本：ID、角点、帧号、时间及定位质量
       |
    PC：协议解析 -> OpenCV IPPE＋LM -> 相对位姿
       |
    PC 墙面码表＋固定的车中心／水平朝右相机假设
       |
    PC 二维全局 x、y、车体 yaw -> 地图及重复定位精度测试

STM32 当前源码中的处理路径：

    合规 UART4 V2 输入（真实 USB 扫码头尚待接口适配）
       |
    UART4_IRQHandler：接收字节及本机微秒时间
       |
    环形缓冲 -> qr_link_poll（每轮最多处理 64 字节）
       |
    qr_parser_feed：帧头、长度、CRC、超时检查
       |
    qr_link：HELLO／会话／序号检查，仅保留最新待处理观测
       |
    qr_decode_observation：恢复 ID、Q4 角点、图像模式、测量时刻
       |
    主循环按最小 50 ms 解算间隔取出最新观测
       |
    qr_localizer_process
       |-- 输入／时间／四边形检查
       |-- 按 ID 查码表，确定有效物理边长
       |-- qr_pnp_solve
       |      去畸变 -> 方形单应性 -> IPPE 两个候选
       |      -> 平移最小二乘 -> LM 精化 -> 重投影／双解检查
       |-- 相对 T_CQ、角度、距离
       |-- 若尺寸、锚点、外参及唯一方向均有效：计算地图车体 x/y/yaw
       |
    QrPoseResult／QR STATUS：输出几何测量及有效标志

与其并行的当前实际里程计路径：

    CANopen 左右轮实际速度 -> motion_poll -> odom_predict
       -> 局部 x_odom、y_odom、yaw_odom -> 遥操／现有导航

未来还需接上的部分：

    轮速增量 ----------------------> 全局 EKF 预测
    有效二维码地图位姿＋实测 R ----> 测量时刻对齐后 EKF 更新
                                       |
                               全局 x_map/y_map/yaw_map

当前主程序没有上述 EKF 调用，二维码解算也没有使用轮速预测作为先验。
当前不是 AMCL、激光匹配、RTAB-Map 或视觉 SLAM。


3. 从像素变成地图坐标，必须具备的五类信息

3.1 每帧观测

    ID：码的解码内容。
    P0、P1、P2、P3：按码体自身方向排序的四个原始图像角点。
    帧号／观测序号／会话号：避免重复和重启后的旧数据混入。
    时间信息：判断观测是否过旧，供后续融合对时。
    图像模式及有效标志：确认数据与内参相匹配。

ESP32 只需提供识别结果及必要元数据，不需要计算距离、姿态或地图坐标。
仅传 ID、不传角点，无法计算相机与二维码之间的连续相对位姿。

3.2 相机内参 K 和畸变 D

由 ost.yaml 标定得到。它们把像素坐标转换为相机中的光线方向。
同为 OV9281 不代表内参可通用；镜头、安装、分辨率、裁剪和缩放必须匹配。

3.3 码的有效物理边长 s

四个角点对应的正方形码体模块区域边长，不包含四周白色静区、纸边或外部标记。
它提供单目测量的米制尺度；没有边长，只能得到距离是“多少个码边长”。
当前算法按正方形建模，不适用于用一个边长描述的非正方形 DataMatrix。

3.4 码在地图中的已知位姿 T_MQ

当前墙面模型至少登记：ID、边长、码中心地图 x/y、码面外法线 yaw。
ID 用于精确查找锚点，ID 本身没有几何位置含义。
单凭 ID 和像素角点，不能推导未知二维码原本在全局地图中的位置。

3.5 相机相对车体的外参 T_BC

描述相机光心在车体中的位置，以及相机光学坐标轴相对车体的方向。
STM32 使用实测六参数，不自动复制 PC 测试页的假设值。
只知道相机看到二维码的相对位置，还不能直接得到车体中心的位置。


4. 坐标系、角点顺序与单位

4.1 地图坐标系 M

    +X、+Y：由建图或人工地图确定的二维轴。
    +Z：竖直向上。
    yaw：车体 +X 在地图中的方向，由地图 +X 朝 +Y 逆时针为正。
    地图原点不等于小车每次上电的局部里程计原点。

4.2 车体坐标系 B

    +X：车头朝前。
    +Y：车体向左。
    +Z：向上。
    原点：项目定义并测量外参时采用的车体定位参考点。

4.3 相机光学坐标系 C

    原点：相机光心。
    +X：图像向右。
    +Y：图像向下。
    +Z：镜头向前，即光轴方向。

注意：相机的 +X 不是小车的前进方向；相机的 +Z 才是镜头看向的方向。
右向安装时，相机光轴指向车体 -Y。

4.4 二维码坐标系 Q

    原点：有效码体正方形的中心。
    +X：码自身正面朝右，沿 P0 -> P1。
    +Y：码自身正面朝上，沿 P3 -> P0。
    +Z：垂直码面向外，朝向观察印刷正面的空间。

在码自身的正面示意中：

                 +Y_Q
                   ^
          P0-------|-------P1
          |        |       |
          |        O------>| +X_Q
          |                |
          P3---------------P2

    +Z_Q 垂直纸面朝读者。

物理角点坐标为：

    P0_Q = (-s/2, +s/2, 0)
    P1_Q = (+s/2, +s/2, 0)
    P2_Q = (+s/2, -s/2, 0)
    P3_Q = (-s/2, -s/2, 0)

图示中的“左上／右上”指码自身的规范方向，不是每帧屏幕中的左右上下。
码或相机转动后，仍必须保持相同的 P0/P1/P2/P3 身份。

本机 STM32_CDC_PROTOCOL.md 说明真实扫码头当前识别 DataMatrix：P3 是两条
实线边的交点，P1 是两条时钟边的交点，输出已映射到原图。
文件及模块名虽然使用 QR，当前相对几何求解处理的是有规范方向的正方形码。
其识别算法在 ESP32 固件中，固件源码不在本工程，不能据此认定其内部实现。

墙面快捷登记函数还要求 Q 的 +Y 实际竖直向上。若把码绕法线旋转 90° 粘贴，
不能仍仅按原先的“竖直、正向”登记；需要正确描述完整方向或修正安装。

4.5 变换记号

    T_AB = [ R_AB  t_AB ]
           [ 0       1 ]

    p_A = R_AB * p_B + t_AB

即 T_AB 把 B 系的点变成 A 系的点。
R_AB 为 3×3 旋转，t_AB 为 B 原点在 A 系中的坐标；代码数组按行存放。

    T_CQ：二维码 -> 相机。
    T_BC：相机 -> 车体。
    T_MQ：二维码 -> 地图。
    T_MB：车体 -> 地图。

4.6 单位

    输入角点：pixel；UART Q4 单位为 1/16 pixel。
    内参 fx/fy/cx/cy：pixel；畸变系数：无量纲。
    协议 side_um：微米，200 mm = 200000 um = 0.2 m。
    内部米制平移、地图 x/y、距离：m。
    核心算法及地图 yaw：rad；相机安装角参数：deg。
    QRGEOM 的 yaw_y_deg/pitch_x_deg/roll_z_deg：deg。
    地图登记函数的 normal_yaw：rad，注意不要直接传入度数。
    时间：us 或 ms，以字段后缀为准；重投影 RMS：pixel。


5. 数据接收、时间恢复与初步拒绝条件

5.1 当前 UART 接收服务

UART4 使用 PC10 TX、PC11 RX，460800 baud，8N1，3.3 V TTL。
中断只保存接收字节和本机单调微秒时刻，不在中断内做 PnP。
主循环先服务电机、CAN、控制与导航，再按每轮 64 字节预算解析扫码数据。

V2 的 QR_CORNERS 类型为 0x10，载荷 96 字节，总帧长 118 字节。
接收器核对 A5 5A 帧头、长度、CRC-16/CCITT-FALSE 和 10 ms 组帧超时。
HELLO 核对标定 ID、1280×720 图像模式及 32 字节 ID 容量。
本版 ID 长度为 1～32 字节，按长度和原始字节精确匹配，不能随意转成整数。
例如文本“01”与“1”不是同一个 ID。

会话 boot_id 改变时清空旧待处理观测与序号状态；包、观测和有效源帧序号
分别去重，允许 uint32 自然回绕。只保留一个最新待处理观测，旧待处理帧可被替换。

协议解析器仍能识别旧的 QR_POSE 类型，但定位函数会以 corners_required
拒绝含上游相对位姿的输入，确保统一 STM32 链路的位姿由 STM32 自己计算。

5.2 角点恢复

    u_px = uq4 / 16
    v_px = vq4 / 16

当前 C 代码要求 0 <= u <= 1279、0 <= v <= 719，图像为原始 1280×720。
角点不能来自网页缩放后的画布坐标，不能重复叠加 ROI 偏移或重复去畸变。
真实 USB CDC 三位小数文本与 UART Q4 的编码不同，接收适配需明确转换。

5.3 观测时刻

本机接收时刻不是图像采集时刻。当前 UART V2 依照报文的年龄模式恢复
本机时基下的测量时刻；模式 0 为兼容的固定延迟估计，模式 1 为逐帧年龄：

    capture_us = rx_end_us - age_us - wire_us

    time_mode=0：wire_us=0，兼容规范约定 age_us=50000，已含线传输年龄。
                这是固定总延迟估计，不是实测每帧拍摄时刻。
    time_mode=1：age_us 不含线传输时间，接收端只补偿一次 wire_us。

    wire_us = ceil(总帧字节数 * 10 * 1000000 / 460800)

118 字节 QR_CORNERS 的 wire_us 为 2561 us。不能重复减去这段时间。
ESP32 的自启动 capture_us 与 STM32 的时钟不是同一原点，不能直接相减。
USB CDC 的设备帧完成时间、发送年龄及本机时间，需另做相应时基适配。

当前解算开始时要求：

    now_us - capture_us < 100000 us

达到或超过 100 ms 拒绝为 observation_stale。
本版记录 time_sigma_us 及其有效性，但尚未将其接入全局融合门控或协方差。
接口中的采集时间还应核对实际语义，例如帧完成时刻与曝光时刻的差别。

STATUS 的 300 ms 新鲜度用于 link_fresh 诊断；当前主循环并不直接以
qr_link_ready() 返回值阻断每次几何求解。不要把它理解为完整融合就绪条件。

5.4 四边形检查

进入几何求解前要求：
    四角为有限数，图像模式与有效标志正确；
    每条相邻边长度 >= 2 pixel；
    四边形按输入顺序保持正向凸性，无交叉、倒序或塌缩；
    四边形面积 >= 8 pixel²。

这只是最低合法性门槛，不表示边长 2 pixel 的码有可用的真实定位精度。
程序不按图像位置自动重排角点，否则会破坏码自身方向与地图方向的对应。


6. 由角点求相对位姿：投影模型与去畸变

6.1 当前固化的内参

    K = [ 733.24251     0          589.27360 ]
        [   0         732.51153   359.37603 ]
        [   0           0           1       ]

    D = [k1, k2, p1, p2, k3]
      = [0.119448, -0.223125, 0.000163, -0.000596, 0.083362]

标定 ID=1，适用原始 1280×720 图像。数值定义在 qr_pose.h，启动时
qr_camera_ov9281() 写入标定结构体。STM32 不需要运行时 YAML 解析库。
这里使用原始 K 和 Brown 畸变系数，不使用校正图像的 projection_matrix。

6.2 物理投影关系

对任一码体角点：

    [Xc, Yc, Zc]^T = R_CQ * P_Q + t_CQ
    x = Xc/Zc，y = Yc/Zc
    r2 = x*x + y*y
    radial = 1 + k1*r2 + k2*r2² + k3*r2³

    xd = x*radial + 2*p1*x*y + p2*(r2 + 2*x*x)
    yd = y*radial + p1*(r2 + 2*y*y) + 2*p2*x*y
    u = fx*xd + cx
    v = fy*yd + cy

PnP 要找的就是能使四个已知码体角点投影到所测四个像素角点的 R_CQ、t_CQ。
旋转有三个自由度，平移有三个自由度；四个角点提供八个标量像素观测。
平面场景可能有两个近似同样好的姿态，观测数量够用不代表姿态一定唯一。

6.3 从原始像素恢复归一化光线

先计算带畸变的归一化坐标：

    xd = (u-cx)/fx
    yd = (v-cy)/fy

以 x=xd、y=yd 为初值，做固定 5 次迭代：

    重新计算 r2、radial、切向项 tx、ty
    tx = 2*p1*x*y + p2*(r2+2*x*x)
    ty = p1*(r2+2*y*y) + 2*p2*x*y
    x_next = (xd-tx)/radial
    y_next = (yd-ty)/radial

得到去畸变的归一化坐标 (x,y)，其对应光线方向为 (x,y,1)。
这是四个角点的计算，不是对整幅 1280×720 图像做去畸变，计算量较小。


7. IPPE 初解：为什么会得到两个姿态候选

源码：app/localization/qr_pnp.c，入口 qr_pnp_solve()。
IPPE 全称 Infinitesimal Plane-Based Pose Estimation，适用于平面目标位姿估计。
本工程实现其数学方法，不链接 OpenCV 的 IPPE 代码或二进制库。

7.1 内部统一按“一个码边长”计算

算法使用辅助坐标系 A：+X 码右、+Y 码下、+Z 指向码内，与 Q 的关系为：

    F = diag(1,-1,-1)
    p_A = F*p_Q

单位正方形角点：

    P0_A=(-0.5,-0.5,0)   P1_A=(+0.5,-0.5,0)
    P2_A=(+0.5,+0.5,0)   P3_A=(-0.5,+0.5,0)

这样内部平移的单位是“码边长”。最终再恢复：

    R_CQ = R_CA*F
    t_CQ_m = t_CA_in_code_sides * s_m

旋转不因边长变化；米制距离与配置的实际边长成正比。

7.2 四点单应性

由于四点在同一平面，用 3×3 单应矩阵 H 描述平面到归一化图像的关系：

    [x,y,1]^T ~ H * [X_A,Y_A,1]^T

    H = [h0 h1 h2]
        [h3 h4 h5]
        [h6 h7  1]

“~”表示齐次坐标成比例。
本工程利用单位正方形的特殊结构闭式计算 H，避免通用 8×8 线性方程求解。
单应矩阵描述投影关系，尚不是已经满足正交约束的完整三维旋转矩阵。

7.3 在码中心分析投影局部变化

码中心的归一化图像坐标 p=h2、q=h5。
单应性在平面中心的一阶导数为：

    J = [h0-p*h6   h1-p*h7]
        [h3-q*h6   h4-q*h7]

构造 V，把光轴方向旋转到中心视线 (p,q,1) 的单位方向。
再消除这段中心视线造成的投影影响：

    E = V[0:2,0:2] - [p,q]^T * V[2,0:2]
    B = inverse(E) * J

计算 B^T*B 的最大特征值，将 B 按其最大奇异值归一化。
剩余问题是在旋转矩阵前两列中，补出尚未知的第三分量 za、zb：

    za² = 1 - ||B第一列||²
    zb² = 1 - ||B第二列||²
    za*zb = -dot(B第一列,B第二列)

这通常允许 (za,zb) 与 (-za,-zb) 两组符号。
经列归一化、正交化和叉积构造第三列，再乘回 V，得到两个旋转初值。
两个候选反映平面姿态的几何歧义，不是识别到了两个不同 ID。

7.4 每个旋转候选分别求平移

对固定旋转，把单位码点旋转后记为 a=R_CA*P_A。
归一化图像点为 (x_i,y_i)，由投影式得到：

    tx - x_i*tz = x_i*a_z - a_x
    ty - y_i*tz = y_i*a_z - a_y

四个点共八个线性方程，未知量仅 tx、ty、tz。
累加为 3×3 最小二乘正规方程，再做带部分选主元的消元。
至此得到最多两个完整相对位姿初值，之后还要进行 LM 优化与质量判定。


8. LM 精化、重投影误差与双解歧义门控

8.1 为什么有初值后还要优化

真实像素角点包含定位噪声、子像素误差和量化误差。初解只提供合理的起点，
不一定使原始畸变像素中的误差最小。程序分别优化每个有效候选。

误差始终在原始带畸变图像中评估：按第 6.2 节投影模型，把候选三维角点
重新投影成 (u_pred,v_pred)，再与 ESP32 输出的原图角点比较。
优化时重新加入畸变是为了与原始观测比较，不是把输入重复去畸变。

    e_i = [u_pred_i-u_i, v_pred_i-v_i]
    cost = sum(i=0..3)[e_u_i²+e_v_i²]
    RMS_px = sqrt(cost/4)

这里除以 4，是四个二维角点各自的欧氏误差均方根；不是除以 8 的标量 RMS。

8.2 每步优化什么

每个候选使用六维局部增量：

    delta = [dwx,dwy,dwz,dtx,dty,dtz]

解析计算八个像素残差对六个增量的雅可比 J，累加 J^T*J 和 J^T*e。
Levenberg-Marquardt（LM）阻尼最小二乘方程为：

    [J^T*J + lambda*diag(max(diag(J^T*J),1e-6))] * delta = -J^T*e

仅解一个 6×6 线性系统。旋转按局部旋转向量更新：

    R_next = exp([dw]x) * R
    t_next = t + dt

[dw]x 是叉乘反对称矩阵，exp 按 Rodrigues 公式计算，小角度使用级数展开。
它不直接把全局欧拉角作为优化变量，避免正面朝向定义自带的 180° 翻转影响。

lambda 初值 0.001；代价下降则接受更新并将 lambda 乘 0.25；
不下降则增大 lambda，乘 8 后重试，重试可复用当前雅可比。
每个候选最多 12 次尝试，两个候选最多合计 24 次；满足收敛条件可提前停止。
次数上限限制计算工作量，不等于已经实测保证某个固定微秒截止时间。

8.3 有效候选的基本要求

    四个码体角点都在相机前方：Zc > 0。
    相机看到的是定义中的码体印刷正面。
    投影及代价为有限数。
    最佳候选最终 RMS <= 2 pixel。

最终返回 Q 系时，正面可见等价于：

    n_C = R_CQ 的第三列
    dot(n_C,t_CQ) < 0

不满足要求则返回 geometry_rejected。
2 pixel 是当前软件门限，不是对距离、角度或地图误差的保证。

8.4 为什么不能总是选 RMS 更小的那个姿态直接定位

如果两个不同姿态投影得几乎一样，即便最小 RMS 很小，当前画面仍可能
不足以可靠区分真实姿态。尤其在码面接近正对、码像素较小或距离较远时。

当前检查最佳结果与其他“原始初值／优化候选”的旋转差异：

    旋转相差 > 1°，且替代候选 RMS <= 2 pixel，才作为不同可行姿态比较。
    gap_px = max(0, 最小替代RMS - 最佳RMS)

若有这样的替代姿态，且：

    gap_px <= max(0.15 pixel, 0.2*最佳RMS)

则 ambiguous=true。
也比较原始初值，是为了避免两个优化过程收敛到同一结果后漏掉初始歧义证据。

本帧仍可保留最佳相对测量用于诊断，但 orientation_unique=false，不生成有效
地图车体位姿。欧拉角奇异也会使 orientation_unique=false。
目前没有通过轮速先验、多帧跟踪或多个码共同优化来自动消除双解。

低 RMS 只说明该候选能较好解释当前四个像素点，不能证明角点没有系统偏移，
也不能证明物理边长、标定、地图锚点和外参准确。


9. 相对结果到底表示什么

9.1 t_CQ 不是“相机在地图中的位置”

    p_C = R_CQ*p_Q + t_CQ

取码中心 p_Q=0，得到 p_C=t_CQ。因此 t_CQ 是“二维码中心在相机系中的位置”：

    tx > 0：码中心在相机图像右侧的空间。
    ty > 0：码中心在相机下方。
    tz > 0：码中心位于镜头前方。

若需要“相机在二维码系中的位姿”，应取逆：

    R_QC = R_CQ^T
    t_QC = -R_CQ^T*t_CQ

不能只把 tx、ty、tz 同时改成负号就当作逆变换。

9.2 三种距离

    码中心直线距离：
        range_m = sqrt(tx²+ty²+tz²)

    光轴深度：
        optical_depth_m = tz

    相机到无限码平面的垂直距离：
        distance_to_plane_m = -dot(n_C,t_CQ)

三者通常不同。第三种是到码所在无限平面的距离，不是自动测得最近障碍距离。
只有在目标与视线关系满足相应条件时，这些数值才会相等或接近。

9.3 尺寸选择和无尺寸情况

当前大小优先级：
    发送端 side_um 非零 -> 使用发送端边长；
    否则查同 ID 的本地码表边长；
    两者都没有 -> 内部按单位边长 1 m 归一化，metric_valid=false。

若发送端和本地码表都提供边长且不相同，仍保留按发送端边长计算的相对结果，
但报告 relative_ok_side_mismatch，不生成地图位姿。这里是精确数值比较。

无实际边长时，可显示：

    range_in_code_sides = ||t_in_code_sides||

例如 10 表示相机到码中心的距离为码边长的 10 倍，不能直接说是 10 m。
此时算法结构体中的米制距离字段为 NAN；诊断可能用有效标志配合 0 占位显示。
旋转仍可以求解，但是否唯一要另看 ambiguous 和 orientation_unique。

9.4 相对偏转角的定义

当码自身正向、正对相机时，Q 的 +Y 与相机 +Y 相反，Q 的 +Z 也与相机 +Z 相反，
所以中性姿态为 F=diag(1,-1,-1)，不能直接把 R_CQ 的欧拉角当作零偏转。

定义：

    A = R_CQ*F
    A = Ry(yaw_y)*Rx(pitch_x)*Rz(roll_z)

当前输出是 Y-X-Z 顺序分解的相对角：

    pitch_x = asin(clamp(R_CQ[1,2],-1,1))
    yaw_y   = atan2(-R_CQ[0,2], -R_CQ[2,2])
    roll_z  = atan2( R_CQ[1,0], -R_CQ[1,1])

上式矩阵下标从 0 开始，属于相机相对测量，不是地图车体 yaw。
大角度下欧拉分解与旋转顺序有关，不能把 yaw_y 直接理解为车体转过的角度。
接近欧拉奇异时程序使用特殊分支显示角度，但不会确认唯一方向。


10. 由相对位姿换算车体地图 x、y、yaw

10.1 二维墙面码表

函数 qr_localizer_add_wall_landmark() 输入：

    ID 字节和长度
    side_um：有效码体边长
    marker_x、marker_y：码中心在地图中的坐标，m
    normal_yaw：码面向外法线在地图 XY 平面中的方向，rad

设 theta=normal_yaw，当前竖直正向墙面码构造：

    R_MQ = [-sin(theta)   0   cos(theta)]
           [ cos(theta)   0   sin(theta)]
           [     0       1       0     ]

    t_MQ = [marker_x,marker_y,0]^T

各列分别是 Q 的 +X、+Y、+Z 在地图系中的方向。
第三列就是码面外法线：

    theta=0°：面朝地图 +X。
    theta=90°：面朝地图 +Y。
    theta=180°：面朝地图 -X。
    theta=-90°：面朝地图 -Y。

该角不是纸面上的箭头角，也不是小车朝向或镜头朝向。
t_MQ 的 z=0 是二维模型的占位值，不代表二维码实际贴在地面上。
本地当前容量 QR_MAX_LANDMARKS=32，默认主程序尚未填入这些实际锚点。
码表只提供定位锚点，不等于拓扑路网、可通行边或障碍边界。

10.2 相机外参

配置文件：app/zlac/qr_installation.h。

    camera_x/y/z：相机光心在车体 B 中的位置，m。
    mount_yaw：从车头 +X 绕 +Z 逆时针，deg。
    pitch_up：光轴向上为正，deg。
    roll：按安装前向轴右手方向，deg。

由 qr_camera_extrinsic_from_mount() 计算：

    R_forward_optical = [ 0   0   1]
                        [-1   0   0]
                        [ 0  -1   0]

    R_BC = Rz(mount_yaw)*Ry(-pitch_up)*Rx(roll)*R_forward_optical
    t_BC = [camera_x,camera_y,camera_z]^T

额外的 R_forward_optical 是光学系与车体系的轴约定转换，不能省略。
相机在车中心、水平朝右，对应 yaw=-90°、pitch_up=0°、roll=0°。
这组值是 PC 测试假设；STM32 当前文件中的相同默认值只是未启用占位值。
必须测量并显式设置 C30D_QR_EXTRINSIC_CONFIGURED=1 后，STM32 才应用外参。
只启用外参不会自动登记码表或启动全局融合。

10.3 完整刚体关系

对同一个码点，存在：

    T_MQ = T_MB*T_BC*T_CQ

因此一般三维形式为：

    T_MB = T_MQ*inverse(T_BC*T_CQ)

这个关系解释了为什么需要相对测量、码表和外参三者。
但当前二维代码不是不加约束地采用完整三维逆变换的平移结果，
而是先提取 yaw、投影到平面后再求 XY，如下一节。

10.4 当前源码实际使用的平面公式

第一步，用三个旋转矩阵得到车体原始方向：

    R_MB_raw = R_MQ*R_CQ^T*R_BC^T
    yaw_B = atan2(R_MB_raw[1,0],R_MB_raw[0,0])

第二步，将车体方向约束为二维：

    R_MB_planar = Rz(yaw_B)

第三步，算码中心相对车体参考点的向量：

    offset_B = R_BC*t_CQ + t_BC

第四步，码中心地图位置减去该向量的地图表示：

    [x_BM,y_BM]^T = [marker_x,marker_y]^T
                    - (Rz(yaw_B)*offset_B)[0:2]

展开即：

    x_BM = marker_x - cos(yaw_B)*offset_B.x + sin(yaw_B)*offset_B.y
    y_BM = marker_y - sin(yaw_B)*offset_B.x - cos(yaw_B)*offset_B.y

最后输出的 x_BM、y_BM、yaw_B 属于车体参考点，不是二维码的位置，
也不是未补偿相机安装偏移的光心位置。
代码只计算需要的旋转元素和 XY，没有进行通用 4×4 矩阵求逆。

10.5 为什么二维地图可以不填写高度

当前假设车体在水平平面内运动、二维码正向竖直贴墙。
求出 yaw 后，Rz(yaw) 不会把竖直分量转成 XY，所以：

    码中心实际高度不参与最终 XY 公式。
    相机位置的 z 分量不参与最终 XY 平移。
    仍保留 STM32 的 z 外参，供完整安装描述使用。

但这不表示可以丢弃像素 v 或把三维相对求解删成单个水平夹角：
四个 (u,v) 仍共同决定三维 R_CQ、t_CQ；相机俯仰／滚转外参仍需准确。

代码计算 tilt=acos(clamp(R_MB_raw[2,2])) 仅作诊断，不因车体倾斜拒绝定位。
取消倾斜拒绝不等于已经补偿真实三维车体倾斜。若车实际明显俯仰、滚转、
码贴歪或墙面不竖直，二维模型仍可能产生偏差。

10.6 与 PC 源码的相同点及独立部分

PC：geometry.py 进行 OpenCV IPPE＋LM；global_test.py 做上述墙面平面换算。
STM32：qr_pnp.c 原生 C IPPE＋LM；qr_pose.c 使用相同坐标定义和二维公式。
两端均采用原始 K/D、正方形四角、正面可见、重投影和双解检查。

两端运行互不依赖：PC 的角点接收、配置和地图测试留在 PC；STM32 自己接收
角点、存储配置、执行解算。两种实现及浮点精度不同，不要求每一位数值相同。
相机外参也不同：PC 固定测试假设，STM32 独立实测设置。


11. 地图文件与网页显示的含义

当前二维码全局定位是“已知 ID 锚点＋相对位姿”，不使用栅格占据概率算匹配分数。
PGM 图像用于表示场地占据情况和显示背景；YAML 提供地图分辨率、原点等。
二维码 PnP 本身不读取 PGM，也不会由 PGM 的黑白图自动识别实际码的安装位姿。

二维码锚点的地图 x/y 必须与地图 YAML 所定义的米制坐标处于同一坐标系。
若从地图像素读位置，要使用分辨率、原点和图像向下的像素 Y 约定进行转换，
不能把图像像素索引直接当成米。
直接测量锚点坐标，或由已知车体位姿反算并独立复测，是标定码表的工作；
不要用同一套未经验证的二维码输出同时充当其自身精度真值。

网页红箭头当前要求表示镜头方向，与定位输出的车体 yaw 是两个量。
对 PC 的水平朝右安装假设：

    yaw_lens_map = wrap(yaw_body_map - 90°)

一般 STM32 安装可将光轴向量 d_M=Rz(yaw_body)*R_BC*[0,0,1]^T
投影到地图，取 atan2(d_M.y,d_M.x) 表示镜头水平方向。
地图点旁的坐标仍应显示车体参考点 x/y；相机位于车中心时两者的位置重合。
最近两秒的红点轨迹是有效定位样本的显示历史，不是新的滤波算法或轮速融合。


12. 与轮式里程计的关系及后续融合原理

12.1 当前已经运行的轮式里程计

motion_poll() 从 CANopen 0x606C 左右轮实际速度得到位移，不使用命令速度代替反馈。
实际反馈单位为 0.1 rpm；默认轮径 165 mm、轮距 0.360 m，仍需实车标定。

    v = 实际反馈值 * pi*轮径_m/600 * 该轮比例系数

每一时间段对左右轮速度分别进行梯形积分得到 dL、dR：

    ds = (dL+dR)/2
    dtheta = (dR-dL)/轮距

odom_predict() 使用圆弧积分：

    h = dtheta/2
    sinc(h) = sin(h)/h，h 接近 0 时使用级数，sinc(0)=1
    x_next = x + ds*sinc(h)*cos(yaw+h)
    y_next = y + ds*sinc(h)*sin(yaw+h)
    yaw_next = wrap(yaw+dtheta)

轮式里程计状态为 [x,y,yaw]，协方差为 3×3，没有 IMU 或陀螺零偏状态。
它提供局部连续运动，但左右轮比例、轮距误差及打滑会使位置和航向逐渐漂移。
当前二维码结果没有写回这个 odom，也没有直接修正现有导航位姿。

确认驱动器失能、MCU 重启或检测到驱动器重启时，局部里程计按既定策略清零。
失能保持原点期间不累计推车位移。空格急刹保持驱动器使能；只要实际轮速
反馈连续有效，仍积分减速过程，不因为发出急刹命令就清零或冻结里程计。

12.2 已有但尚未接入的全局 EKF 内核

源码：app/localization/global_ekf.c/.h。
这是三状态轮速＋二维码融合内核，默认主程序没有调用，未使用的函数由链接器回收。
下列公式说明准备接入后的数学关系，不表示当前 HEX 已在运行该融合。

    状态 X = [x_map,y_map,yaw_map]^T
    轮速增量 ds、dtheta -> 使用圆弧模型预测 X_minus
    P_minus = F_state*P*F_state^T + G*Q*G^T

二维码给出同一时刻、同一车体参考点的地图测量：

    z = [x_qr,y_qr,yaw_qr]^T
    innovation = [z.x-X_minus.x,
                  z.y-X_minus.y,
                  wrap(z.yaw-X_minus.yaw)]^T

直接观测三个状态，H=I：

    S = P_minus + R
    d2 = innovation^T*inverse(S)*innovation
    d2 超过配置的马氏距离门限 -> 拒绝异常更新

    K = P_minus*inverse(S)
    X_plus = X_minus + K*innovation
    yaw_plus 再归一化

    P_plus = (I-K)*P_minus*(I-K)^T + K*R*K^T

最后一式是 Joseph 协方差更新形式。
核函数使用小矩阵和单精度，不依赖外部 EKF 库。

R 是地图 x/y/yaw 的测量协方差，对角线单位为 m²、m²、rad²，
位置与角度交叉项单位为 m*rad。重投影 RMS 的单位是 pixel，两者不能直接替换。
当前几何结果 covariance_valid=false，9 个协方差元素初始化为 NAN，
程序没有根据 RMS、score 或码距自动生成可信 R。
后续需从实测重复性和独立真值误差估计 R，并考虑距离、观察角、像素质量、
时间误差，以及码表和外参中的系统偏差。

12.3 动态运动时必须按测量时刻融合

二维码描述采集那一时刻的车体位姿。若整车向前运动，而把延迟二维码结果
直接作为“现在的位置”融合，会把运动期间已经发生的位移拉回去。

理想匀速时，未处理延迟造成的量级可近似估计：

    位置错位约为 v*延迟
    航向错位约为 omega*延迟

例如 v=0.5 m/s、延迟 50 ms，对应约 25 mm；omega=30°/s 时对应约 1.5°。
实际还叠加角点噪声、曝光运动模糊、外参及码表误差。

后续需要在 capture_us 时刻执行观测更新，再按时间顺序重放之后的轮速预测
和其他已接受观测，回到当前时刻。已有局部历史并不等于已经完成这项功能。
仅丢弃超过 100 ms 的旧帧、仅取最新帧或提高网页刷新率，也不等于完成延迟补偿。
相机视频与检测画面不同步是另一类显示时间问题，不能直接作为几何误差的结论。


13. 状态标志、诊断与常见结果的正确解释

13.1 必须分别看三层有效性

    relative_valid=true：四角点成功产生一个通过几何门限的相对测量。
    metric_valid=true：具有物理边长，可用米制尺度解释相对平移和距离。
    QrPoseResult.valid=true：成功生成车体在地图中的 x、y、yaw。

还要同时看：
    ambiguous：是否存在不能可靠区分的平面双解。
    orientation_unique：是否没有双解歧义和欧拉奇异。
    covariance_valid：是否具备可用于融合的观测协方差；当前为 false。
    capture_age_us：本帧是否仍然新鲜。

qr_localizer_process() 返回 true，以及 accepted 计数增加，表示相对几何成功。
它们不等同于地图位姿有效，更不等同于已完成融合。
未知 ID、未设置外参或双解歧义时，都可能返回 true 而 result.valid=false。

13.2 当前地图位姿生成的必要条件

    有物理尺寸；发送端尺寸与码表尺寸不冲突；
    ID 在本地表中；方向唯一；
    STM32 外参有效；该码表项有地图位姿；
    地图换算结果为有限数。

源码检查按上述先后顺序报告原因，同一帧可能还有其他尚未检查到的缺项。

常见 reason：

    waiting
        尚无观测。
    observation_stale
        观测过旧；可能是处理入口拒绝，也可能是诊断时已经超龄。
    invalid_observation / invalid_corners
        模式、时间、标志或四角点不符合要求。
    corners_required
        收到了上游相对位姿，当前 STM32 路径要求只传角点。
    geometry_rejected
        几何解失败、不可见或重投影超限等。
    relative_ok_size_not_configured
        相对测量成功，但没有米制边长。
    relative_ok_side_mismatch
        发送端边长与本地边长不一致。
    relative_ok_unknown_id
        相对测量成功，但 ID 没有登记。
    relative_ok_orientation_ambiguous
        相对测量成功，但平面双解无法可靠区分。
    relative_ok_euler_singular
        相对角度处于奇异情况。
    relative_ok_extrinsic_not_configured
        缺少有效 STM32 相机外参。
    relative_ok_map_entry_not_configured
        仅登记了尺寸，未登记地图位姿。
    relative_ok_map_geometry_rejected
        地图换算失败。
    map_pose_ok_covariance_unconfigured
        地图几何位姿有效，但协方差尚未配置，不能据此自动融合。

13.3 QR STATUS / NAV QR STATUS

通过现有控制串口命令通道查询，不是把命令发到接收角点的 UART4。

    QRSTATE：握手、状态新鲜度、配置状态等。
    QRCOUNTS：收到的帧、观测、替换、拒绝、CRC／超时等计数。
    QRGEOM：相对有效性、角度、距离、地图坐标、RMS、歧义与耗时。

注意当前 QRSTATE 中的 map_valid=0、global=WAIT_REFERENCE 为默认固定声明，
不是每个观测实时求解后的地图状态。具体几何结果看 QRGEOM 的 map_valid。
当前主程序缺少实际配置时，本来就不应有真实有效的地图结果。

诊断会把超龄结果的主要有效标志置 0，部分数值字段仍可能保留上次结果。
不能仅因坐标数字还在就继续使用；必须检查 freshness 和对应有效标志。


14. STM32 计算负担和延迟的含义

降低计算量的当前做法：

    ESP32 传 ID＋四角点，STM32 不接收或处理整帧图像。
    单精度 float，使用 Cortex-M4F 硬件 FPU；固定小数组，不做算法堆分配。
    四角点固定 5 次去畸变；正方形闭式单应性；2×2 特征值及 3×3 平移求解。
    两候选各最多 12 次 LM 尝试；解析雅可比；累加对称矩阵上三角；收敛提前退出。
    主程序解算开始间隔至少 50 ms，名义上限 20 Hz，等待时只保留最新观测。
    不做通用 4×4 求逆、不推断二维模型不需要的车体高度。
    IMU 不参与，轮速里程计和待接入全局内核均为三状态。

PnP 在主循环中同步执行，有次数上限；它不是独立的可抢占低优先级任务。
中断仍可运行，但主循环内的其他服务要等该次求解返回，因此仍需实板检查
最坏耗时、CAN 反馈连续性和看门狗余量。20 Hz 上限不是保证实际达到 20 Hz。

当前算法只 include 项目头和 math.h、string.h 等标准头。
默认工程底层使用能在 STM32 上运行的 ST SPL、CMSIS-Core 及工具链运行库
newlib-nano、libm、libgcc、libnosys；未引入 Eigen、OpenCV 或 CMSIS-DSP。
不使用 Eigen 是本工程的计算和依赖选择，不表示所有 Eigen 功能都不能在 MCU 运行。

QRGEOM：

    solve_us：主循环本次调用 qr_localizer_process 前后测得的经过时间。
    max_solve_us：本次运行以来的该处理耗时最大值。
    lm_steps：两个候选合计的 LM 尝试次数。
    candidates：有效初始候选个数，最多 2。

solve_us 包含该处理函数的检查、求解、地图换算及期间中断引入的经过时间，
不包含 ESP32 图像处理、前面的链路排队和网页绘制；不是纯 PnP 内核时间。
它也不是完整端到端延迟，更不是 ESP32 或 STM32 的 CPU 占用百分比。
本次文档核对未进行实板测时，不能把主机测试耗时当成 F407 实际耗时。


15. 用当前 C 源码复算的一组示例

下面是理想投影再进行 Q4 量化的合成数据，用于验证公式和说明单位，
不是实车采样、不是物理定位精度承诺，也没有向实车发送任何命令。
通过 tests/qr_pose_reference_host.c 主机适配器调用现有同一份 C 算法。
该适配器只用于离线核对，不进入 STM32 固件或 PC 生产解算链路。

15.1 输入配置

    内参／畸变：使用第 6.1 节数值。
    码 ID：A，边长 200 mm。
    码中心地图位置：(3.000,1.000) m。
    码面外法线：+90°，即朝地图 +Y；传入 C 函数为 pi/2 rad。
    相机：车体中心、水平朝右，外参 yaw=-90°，其余角和位置为 0。
    合成车体真值：(2.000,3.000) m，车体 yaw=+20°。

由理想姿态投影后按 1/16 pixel 量化的角点：

    P0 = (475.2500,326.8125)
    P1 = (535.0000,325.8750)
    P2 = (535.0000,392.8750)
    P3 = (475.2500,391.9375)

这组配置在测试中显式登记了码表和外参；默认实车启动仍然没有该测试码表。

15.2 C 解算输出（数值取近似）

    relative_valid=1，metric_valid=1，map_valid=1
    ambiguous=0，orientation_unique=1
    candidates=2，lm_steps=6
    RMS=0.002831 pixel，替代候选误差差约 1.296 pixel

    t_CQ = (-0.255823,-0.000010,2.222706) m
    到码中心的直线距离约 2.237379 m

    地图车体 x=2.000965 m
    地图车体 y=3.001948 m
    地图车体 yaw=19.955069°

该输入的理想未量化 t_CQ 约为 (-0.255652,0,2.221405) m，
负 tx 表示码中心在相机左侧。可见光轴深度和直线距离不是同一数值。
地图红箭头若表示镜头方向，此例应约为 19.955069°-90°=-70.044931°。

15.3 正对码面的例子说明双解门控

同样 200 mm 的理想正对码，t_CQ=(0,0,2) m，经畸变投影和 Q4 量化：

    P0=(552.5625,322.7500)   P1=(625.9375,322.7500)
    P2=(625.9375,396.0000)   P3=(552.5625,396.0000)

当前 C 算法得到约 0.01835 pixel RMS、约 2.0005 m 深度，
但 ambiguous=1、orientation_unique=0，地图位姿无效。
这说明很小的像素拟合误差也可能没有唯一可靠方向，不能绕过歧义标志。

15.4 已有 PC／STM32 数值核对的边界

build/tests/wheel-qr-reference-validation.txt 记录了 500 组合成噪声和 Q4
量化观测的数值对照，覆盖不同距离和旋转；39 组双解歧义判定全部一致。
最大旋转矩阵元素差约 0.00050265，最大平移范数差约 0.00012722 m，
最大 RMS 差约 0.00003864 pixel。
这些是 PC 与 C 两种数值实现对同一合成输入的差异，不是实车绝对精度。
实际精度仍需独立量测真值，并统计每次重新到位的重复性和真值偏差。


16. 真正跑通“扫码头＋轮速全局定位”仍需完成的事项

按依赖关系整理如下，不能只修改外参宏后就认为全部完成：

    1）接通真实传输接口。
       实现 USB Host CDC 复合设备选择和文本协议接收，或让扫码头提供
       兼容 UART4 V2 的输出。无需让 PC 中转位姿。
       若使用 USB CDC，需筛选其 quality==2、四边完整等定位质量字段，
       正确处理原始 ID、源帧去重、设备重启及本机测量时刻。

    2）装载实测配置。
       内参对应实际图像模式；边长对应模块外边界；STM32 独立测量外参；
       登记每个墙面码的 ID、边长、地图 x/y 和外法线方向。
       完成码表持久化、版本及开机加载，而不是只填一组测试坐标。

    3）先验证独立二维码地图测量。
       静态检查坐标、朝向、距离及双解；多位置、不同角度、不同距离复测，
       独立区分标定／码表系统误差、角点噪声和动态测量延迟。

    4）测量延迟与协方差。
       实板统计 solve_us/max_solve_us，校验时间语义与端到端年龄；
       从实测建立二维码 R 和轮速噪声参数，设置异常门限。

    5）把全局 EKF 与生命周期接入主程序。
       同时接入连续预测、首个可靠锚点初始化、观测时刻更新和历史回放；
       建立 WAIT_REFERENCE/TRACKING/DEGRADED/LOST 等状态转换；
       明确重启／失能后的全局重新初始化规则，保持局部清零策略；
       维护 map 与 odom 的关系，并让导航明确使用需要的坐标系。

    6）完成上板及场景验收。
       验证计算负载、CAN／控制服务连续性、掉码／遮挡／重启、重复定位和
       动态误差，再开放导航使用融合结果。当前文档任务没有执行烧录。
